# AgriSmart AI — Data Readiness Assessment

Generated by direct repository audit (see git history / commit for date)
and reproducible any time via `npm run ai:prepare`.

## What exists today

| Source | Real records? | Notes |
|---|---|---|
| `Telemetry` (Mongo time-series) | **0** persisted | Schema exists, ingestion path (`telemetry.service.js`) is fully implemented and tested, but no `mongod` instance is running in this environment and `.env`'s `MONGODB_URI` points at a local dev Mongo with nothing in it. |
| `IrrigationEvent` | **0** persisted | Same — schema + logic exist, no data. |
| `scripts/demoSimulator.js` | 0 persisted (by design) | Boots an **ephemeral in-memory MongoDB** for a live demo; discarded on process exit. Proves the pipeline works end-to-end, is not a data source. |
| CSV/export files anywhere in the repo | none found | Confirmed by full-repository search. |

**Conclusion: zero real agricultural telemetry currently exists.** This
is the expected state for a pre-launch IoT product with devices not yet
deployed to real fields, and this assessment says so plainly rather
than inventing a more favorable number.

## Available features (once real data exists)

From `Telemetry.readings`: `soilMoisturePercent`, `temperatureCelsius`,
`soilSalinityPpt`. From `IrrigationEvent`: `startedAt`, `endedAt`,
`actualDurationSeconds`, `plannedDurationSeconds`, `triggeredBy`. From
`Valve`: per-device `autoOpenBelowPercent` / `autoCloseAbovePercent`
thresholds (used as the supervised label's threshold, not invented).

Derived features implemented in `ai/features/featureEngineering.js`:
lagged moisture (1h/3h/6h), 1h moisture change, 3h rolling average, 6h
rolling min/max, linear 6h trend, hours since last irrigation,
irrigation minutes in the last 6h/24h, hour of day, day of week.

## Sampling frequency / historical depth

Not yet knowable from real data (none exists). The demo simulator uses
a 4-second tick deliberately for a live presentation — **this is not
representative of a real deployment's cadence** and must not be used
to estimate real sampling frequency. `ai/data/syntheticDevData.js`
instead assumes a more realistic 15-minute duty-cycled reporting
interval for pipeline testing.

## Missing values / data quality

Not yet measurable against real data. The loader
(`ai/data/telemetryLoader.js`) already handles the general case: a
telemetry document with no valid `soilMoisturePercent` is dropped and
counted, never imputed or guessed at the ingestion boundary.

## Is there enough real data for supervised learning? **No.**

`ai/training/train.js` enforces `MIN_REAL_EXAMPLES = 500` labeled
examples before it will train and register a model as
`dataSource: 'real'`. At zero real telemetry readings, this bar is not
close to being met.

## What must be collected before a real model can be trained

1. At minimum, several devices reporting for **30+ continuous days**
   at a real duty-cycled interval (15–30 min is a reasonable target —
   matches `ai/data/syntheticDevData.js`'s assumption).
2. A realistic mix of moisture trajectories: natural drying, at least
   several dozen real irrigation events per device (so the "will cross
   threshold" label has enough positive examples — the synthetic
   generator produces roughly a 9–10% positive rate, real soil/climate
   conditions in Egypt may differ substantially).
3. Multiple devices/farms, not just one demo device, so a future
   per-device or per-farm holdout split (noted as a limitation in
   `ai/training/splitChronological.js`) is possible.
4. Consistent `Valve.autoOpenBelowPercent` configuration per device
   (already a schema field — just needs real farmers to have set it,
   or a sane default to stay in place).

## Estimated minimum useful dataset structure

- ≥ 3 devices, each reporting ≥ 30 days at ≤ 30 minute intervals →
  ~4,000+ raw readings/device, ~500–1,500 labeled examples/device after
  the "already below threshold" and "no future label yet" exclusions
  in `ai/data/datasetBuilder.js`.
- ≥ 500 total labeled examples (the `MIN_REAL_EXAMPLES` gate) before
  `ai/training/train.js` will even attempt to certify a model as
  `dataSource: 'real'`.

Until then, `npm run ai:train` will keep producing `dataSource:
'synthetic-dev'` models — by design, not a bug.
